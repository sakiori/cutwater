## Context

The first cutwater release covers npm and Cargo. Maven brings what the other ecosystems lack: snapshots on the default branch, versions passed on the command line, and deployments that are not atomic across a reactor. Maven's CI-friendly versions, `${revision}` with the flatten plugin, are the established practice this change builds on. The version manifest that every ecosystem shares already exists for this reason: a Maven unit's committed files hold its next snapshot, so its released version lives in the manifest.

## Decisions

### Snapshots everywhere, released versions only in release builds

The committed `revision` of every unit is its next snapshot. A dependent refers to a producer through a version property that also holds the producer's snapshot, so a change to a producer and its dependents fits in one merge request and builds in one reactor. Release builds cover only the units the release publishes, one per Maven invocation in dependency order. Each build passes the released versions from the manifest on the command line and installs the unit into a job-local repository for the dependents that follow. Producers the release does not publish resolve from the deploy repository, so a dependent is built against what consumers will actually get. Command-line properties do not reach a deployed POM, so the flatten plugin must interpolate dependencies as well as `revision`. `goal` inspects the POMs that would be deployed for snapshots and unresolved properties. A released unit therefore never depends on a snapshot, and the default branch never carries a release version.

Alternative: commit the released version and add a second "snapshot bump" request, as release-please's Java strategy does. Rejected because between the two merges the default branch carries a release version. Every snapshot deployment from it then tries to redeploy a released version, which release repositories reject.

Alternative: commit the producer's released version in dependents. Rejected because a change that spans a producer and its dependents would then need two merge requests and a release in between.

### Deployment file by file

Maven deployment is not atomic across a reactor, nor within a module: the deploy plugin uploads a module's POM, then its main artifact, then the attached ones, and a run that stops between them leaves a POM without its JAR. A module therefore counts as deployed only when the deploy repository holds every file its release build installed into the job-local repository, not when its POM or the repository's metadata, which Nexus and Artifactory rebuild themselves, says so. `publish` builds and installs the unit first, asks the repository for each installed file, and uploads each missing one with the deploy plugin's `deploy-file`, naming the installed POM and the `pom` packaging, so that the plugin uploads that file alone and neither a second POM nor one it takes from a JAR; the POM goes last. It then asks the repository again and counts what it holds, not what Maven printed, so that a failed upload with a misleading message is not taken for a present file. A retry thus completes an interrupted deployment, also within a module, without uploading again what a release repository would refuse to replace; a file the repository holds without its SHA-1 gets that SHA-1 alone. A file whose SHA-1 there does not match it stops the deployment before any upload: Maven's default checksum policy only warns, consumers that check checksums refuse the file, and a repository that refuses replacements keeps the wrong SHA-1 until the file is deleted there.

A retry rebuilds the unit. Without a reproducible build the new files differ from those already uploaded, and completing a module would mix two builds in one release: a signature or an SBOM computed from bytes the repository does not hold, never to be replaced. Before completing a module the repository partly holds, `publish` therefore compares the files it holds, which the question downloads anyway, with the new build's, and uploads nothing on a difference. Resumable deployments thus need reproducible builds, with `project.build.outputTimestamp` set; a module the repository holds entirely, or not at all, needs no comparison. A detached signature or attestation, `.asc`, `.sigstore` or `.sigstore.json`, carries its creation time and differs whenever it is made again, so it is judged by the file it signs: a held signature stands when that file matches, a missing one of this build goes up, and one whose file is missing or differs stops the deployment. Maven keeps no checksums of these files, as its resolver omits them, so none is asked for or uploaded.

The repository is asked once per round, with one Maven invocation: a generated reactor with one project per file, run with `--fail-at-end`, in which each project's `validate` phase resolves its file with the dependency plugin's `list-classes`. That goal asks Maven Resolver for the artifact alone, without reading its POM, and saves it, with its SHA-1 where the repository has one, into the local repository; it then fails for a file that is no JAR, which changes nothing about what it resolved. A file is missing only where Maven names exactly that file as not found; any other failure, a transfer failure among them, leaves the whole round unanswered. The run keeps the local repository of the answers, so that a held file is downloaded once and later rounds ask, with `--update-snapshots`, only for what was missing; the copy of a file whose SHA-1 the run uploads is dropped, so that the next round fetches both. The deployment found by the first round's effective POMs serves the run's later rounds.

Alternatives for the questions: one `dependency:get` per file, rejected for a JVM per file; one project that depends on every file, resolved with `dependency:resolve`, rejected because collecting dependencies reads each file's POM, so a deployed POM that imports an external BOM or keeps an external parent makes every other file of the module look missing; `dependency:get` and `dependency:copy` in the reactor, rejected because both read the artifact's POM too; and `dependency:copy` with every file as an `artifactItem` of one execution, rejected because it stops at the first missing file.

Alternative: `mvn deploy --projects` for the modules with missing files. Rejected because it uploads every file of those modules again, which a release repository refuses for the files it holds.

Maven Central's Portal publishes atomic bundles and Nexus staging repositories hide unreleased deployments. Both need their own target types and are out of scope here.

### Questions to the deploy repository alone

`publish` decides from what the deploy repository holds, so its questions must reach that repository alone. Maven adds the repositories of active settings profiles to every resolution and sends requests to a repository's mirror, while `mvn deploy` writes to the repository itself. The questions therefore run outside the repository's build, with a local repository of the run's own, empty at first, and settings of their own: the `<server>` entries of the deploy repository and of the mirrors copied as written, so that `${env.…}` references and passwords encrypted with the user's settings-security keep working, the settings-security file the build's command line names, the proxies, and the mirrors, each excluding the deploy repository, but no profile and no other repository. The mirrors stay, with their credentials, because Maven resolves the plugins of the questions through them, where a network reaches Maven Central only through a mirror. The settings are found as the build finds them: through `MAVEN_ARGS` and the `.mvn/maven.config` nearest to the unit's directory, with paths relative to it. The plugins are resolved once per run into a directory that later questions read as the tail of their local repositories. The tail, the reading of `.mvn/maven.config` and the resolver's checksum defaults need Maven 3.9, so a run checks `mvn --version` once, before its first Maven step, and refuses an older Maven.

### Dependents follow their producers

A Maven version without brackets does not float: the deployed POM of a dependent names one version of each producer, and Maven's nearest-wins mediation gives that version to the dependent's consumers. A reference therefore accepts only the exact version the dependent's last release named, and the rule that releases a dependent when a producer leaves its range releases every dependent of a released producer with a patch, as release-please's Maven workspace plugin, Nx and the Maven release plugin do. Only references consumers resolve count: `compile`, `runtime` and imported dependencies and parents; `test`, `provided`, `system` and optional dependencies and plugins do not. A version that a BOM's `dependencyManagement` manages releases the BOM with the managed unit, which is a BOM's purpose, without ordering their publication, since nothing needs the managed unit to build the BOM; so a BOM that manages a unit importing it makes no cycle.

Alternative: references without a range, so that a dependent is released only by its own changesets. Rejected because consumers of the dependent would keep getting the producer's old version until the dependent happens to be released.

### Release commits and command-line versions

Publication happens from the release commit, as for every ecosystem. For Maven this matters more: a Maven build passes the version on the command line, so a build of a later commit under the released version would not even notice that it builds unreviewed code.

## Risks and open points

- The Maven adapter reads POMs without running Maven. Dependency versions that inheritance or profiles change are outside edge discovery, and integration tests against real Maven confirm the supported cases.
- The deploy repository must be reachable with Maven's built-in transports, as the questions run outside the build and its extensions.
